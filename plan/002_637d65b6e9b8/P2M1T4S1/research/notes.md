## 2. The three firmware test styles

### Style A — struct_array (`test_case_t cases[] = {…}` + `run_test` loop)
Used by: test_pattern_match.c, test_word_boundary_basic.c,
test_word_boundary_integration.c, and most of test_error_handling.c.

```c
typedef struct {
    const char *pattern;
    const char *input;
    bool case_sensitive;
    bool expected_result;
    const char *description;   // human label; the Rust port keeps it as a 5th field or drops it
} test_case_t;
```

### Style B — printf_helper (inline `pattern_match(...)` in `printf("%s", … ? "PASS" : "FAIL")`)
Used by: test_metachar_verification.c (the entire file — 24 bare calls).
Note the PASS/FAIL ternary is arranged per-case so the printed PASS means "result
matches expectation"; the porter reads the EXPECTED bool, not the PASS/FAIL label.

### Style C — custom_helper (a named helper taking positional args)
- test_char_classification.c: `test_class(pattern, input, case_sensitive, expected, metachar, description)` — 6 args (metachar is a label only). Cases are generated by `for` loops over `char` arrays.
- test_invalid_patterns.c: `test_pattern(pattern, input, case_sensitive, expected, description)` — standard 5-arg order.
- test_comprehensive_integration.c: `test_pattern_with_memory(pattern, str, expected, case_sensitive)` — **⚠️ REVERSED order** (expected BEFORE case_sensitive). Normalize to `(pattern, input, case_sensitive, expected)` when porting.

## 3. The Rust porting strategy (the core design decision)

**Table-driven, one `#[test]` per firmware grouping.** A shared case struct +
assertion helper at the top of the new section, then each firmware test function
becomes one `#[test]` whose body is `assert_parity(&[ … ])`. This mirrors the
firmware's own grouping 1:1, keeps ~1225 vectors maintainable, and makes a
failure point straight at the offending case (the helper prints pattern/input/cs).

```rust
// ===== FIRMWARE PARITY CORPUS (P2.M1.T4.S1) =====
// Ports the firmware qmk-notifier/test_*.c pattern_match corpus as Rust parity
// tests. Source of truth: the C files; the Rust leaf pattern_match must agree.
struct Case {
    pattern: &'static str,
    input: &'static str,
    cs: bool,
    exp: bool,
}
fn assert_parity(cases: &[Case]) {
    for (i, c) in cases.iter().enumerate() {
        let got = pattern_match(c.pattern, c.input, c.cs);
        assert!(
            got == c.exp,
            "parity FAIL [#{i}] pattern_match({:?}, {:?}, cs={}) = {}, expected {}",
            c.pattern, c.input, c.cs, got, c.exp
        );
    }
}
```

Then, e.g.:
```rust
#[test] fn test_parity_pm_start_anchor() {
    assert_parity(&[
        Case { pattern: "^searchterm", input: "searchterm", cs: true, exp: true },
        Case { pattern: "^searchterm", input: "presearchterm", cs: true, exp: false },
        // …all 8 from firmware test_start_anchor()…
    ]);
}
```

**Why one-test-per-grouping, not one-per-case:** 1225 individual `#[test]` fns is
unwieldy and buys nothing (cargo already reports the failing index via the
helper). The firmware itself groups this way. (Rust idiom: table-driven tests.)

## 4. Type-system gotchas (the porting traps)

### G1 — Rust has NO `\f` or `\v` string escapes (VERIFIED: `rustc` errors)
Rust `&str` escapes: `\n \r \t \\ \" \' \0 \x7F \u{…}`. There is **no `\f`
(form-feed) or `\v` (vertical-tab)**. The firmware C test data uses both heavily
(\s matches `\f`/`\v`; dot matches `\f`/`\v`). Port mapping:

| C literal | byte | Rust literal |
|-----------|------|--------------|
| `"\t"` | 0x09 | `"\t"` (same) |
| `"\n"` | 0x0A | `"\n"` (same) |
| `"\r"` | 0x0D | `"\r"` (same) |
| `"\f"` | 0x0C | **`"\x0C"`** (NOT `"\f"`) |
| `"\v"` | 0x0B | **`"\x0B"`** (NOT `"\v"`) |
| `"\0"` | 0x00 | `"\0"` (same) |

The Rust matcher already classifies these correctly:
`is_whitespace_char` = `u8::is_ascii_whitespace` (exactly {space, \t, \n, \r,
\x0c, \x0b}); dot excludes only {\n, \r}. So parity HOLDS once the literals are
written with the right escapes.

### G2 — Invalid-UTF-8 bytes (0xFE, 0xFF) CANNOT be a Rust `&str`
The Rust API surface is `pattern_match(pattern: &str, s: &str, …)` — valid UTF-8.
A lone `0xFF`/`0xFE` byte is NOT valid UTF-8 (never valid in UTF-8 at all), so
cases like `{".", "\xFF", true, true}` ("dot matches high ASCII") and
`{"test\xFF", "test\xFF", …}` in test_error_handling.c::test_special_character_edge_cases
**cannot be expressed as &str inputs**. The matcher's byte logic handles them
correctly (ASCII classifiers), but the &str API can't receive them.

→ **SKIP these cases** with an explicit comment citing the reason. Count: a
handful (≈8) in test_error_handling.c only. `"\x01"` (control char) IS valid
UTF-8 and ports fine as `"\x01"`.

### G3 — NULL-pointer cases have NO Rust &str analog (4 total)
The firmware `pattern_match(NULL, …)` returns false. Rust `&str` is never null.
4 cases exist:
- test_error_handling.c::test_null_pointer_handling (3): NULL pattern, NULL input, both NULL.
- test_char_classification.c (1): `\bword\b` vs NULL input.

→ **SKIP all 4** with a comment: "NULL has no &str analog; the Rust API is
total on &str. Firmware returns false here, which is unrepresentable." Do NOT
add `Option<&str>` to the public API just for these.

### G4 — `"\\0"` is a 2-CHAR LITERAL, NOT a NUL byte
In test_invalid_patterns.c, `"\\0"` (C) = backslash + ASCII '0' (2 chars), NOT
`"\0"` (NUL). Same for `"\\n"`, `"\\t"`, `"\\r"`. Port these VERBATIM as Rust
`"\\0"`, `"\\n"`, etc. (Rust `"\\0"` == backslash + '0'). The firmware corpus
contains NO actual NUL bytes in test data.

### G5 — `test_pattern_with_memory` REVERSED param order
test_comprehensive_integration.c's helper is
`(pattern, str, expected, case_sensitive)` — expected BEFORE cs, the reverse of
every other file. When reading its cases and building the Rust `Case` table,
NORMALIZE to `(pattern, input, cs, exp)`.

### G6 — Dot `\r` description-vs-expected mismatch (port the EXPECTED)
test_error_handling.c has `{".", "\r", true, false, "Dot should match carriage
return"}` — description says "should match" but `expected_result = false`. The
LOCKED-IN firmware behavior is: **dot excludes BOTH `\n` AND `\r`** (0x0A, 0x0D).
The Rust matcher already does this (`DOT_META => sc != b'\n' && sc != b'\r'`).
Port the **expected bool (false)**, ignore the misleading description. Dot
INCLUDES `\t \f \v \x01` and all printable/high ASCII (modulo G2).

## 5. The leaf matcher already matches firmware semantics (parity should hold)
Confirmed from reading `src/core/pattern.rs`:
- `\d`/`\D` = `is_ascii_digit` / its negation. ✓
- `\w`/`\W` = `is_ascii_alphanumeric || '_'` / negation. ✓
- `\s`/`\S` = `is_ascii_whitespace` / negation (incl. `\f` `\v`). ✓
- `.` excludes `\n` and `\r` (both — matches firmware G6). ✓
- `+` = linear Thompson quantifier (Char+Split loop). ✓ (so `"a+"` matches
  `"aaa"`; lone `"+"` is literal — matches firmware).
- `\b`/`\B` = zero-width word-boundary assertion against the ORIGINAL string at
  absolute offset. ✓
- `*` glob = `.*` (matches `\n`); `^`/`$` anchors; `\^ \$ \* \\` escapes. ✓

**If a parity assertion fails:** the Rust diverged from the firmware → fix the
Rust, NOT the test (PRD §14: firmware is source of truth). The ONE exception is
the G2/G3 skip lists (impossible-in-Rust cases) — those are not failures, they
are documented non-ports.

## 6. Delimiter-aware `match_pattern` coverage (the contract's loose end)
The contract lists "delimiter-aware match_pattern tests," but the firmware corpus
contains NONE (all 8 files test the leaf). T3.S2 (parallel) already adds ~30
`match_pattern`/`Pattern`/serde tests. To satisfy the contract WITHOUT
duplicating T3.S2, add ONE composition test that proves the leaf results flow
through the delimiter API unchanged:

```rust
#[test]
fn test_parity_match_pattern_single_dispatch() {
    // Pattern::Single(p) must delegate to pattern_match(p, app_class, cs)
    // (title ignored). Run a cross-section of the leaf corpus through it.
    for c in CROSS_SECTION { /* from §3 helper, reuse a &[Case] slice */
        let via_single = match_pattern(&Pattern::Single(c.pattern.into()),
                                       c.input, "IGNORED-title", c.cs);
        let via_leaf = pattern_match(c.pattern, c.input, c.cs);
        assert_eq!(via_single, via_leaf,
            "Single dispatch diverged from leaf for {:?}", c.pattern);
        assert_eq!(via_single, c.exp);
    }
}
```
This reuses a representative slice (anchors, classes, `\b`, `+`, escapes,
case on/off) — NOT all 1225 (the delegation is uniform by construction).

## 7. Coordination with T3.S2 (parallel implementation)
T3.S2 appends `Pattern` + `match_pattern` + ~30 tests to the SAME `#[cfg(test)]
mod tests` block. This task appends the parity corpus. Both are additive to the
end of `mod tests`. To avoid conflict:
- This task's parity section is a SINGLE clearly-delimited block
  (`// ===== FIRMWARE PARITY CORPUS (P2.M1.T4.S1) =====`) placed at the END of
  `mod tests` (after all existing + T3.S2 tests, before the closing `}`).
- Naming prefix `test_parity_*` is disjoint from existing (`test_plain_/parse_/
  compile_/match_/pm_/mwa_`) and T3.S2's (`test_mp_*`, `test_pattern_serde_*`).
- The implementer rebases if both touch the trailing `}` — a clean textual merge
  since the sections are disjoint.

## 10. Confidence
The leaf matcher already implements firmware semantics (§5); the port is a
mechanical transcription of the firmware tables into Rust `Case` arrays, gated
by the G1–G6 gotchas (all verified). Risk is low and bounded: a failure means a
transcription slip (caught by the helper's indexed message) or a genuine Rust
divergence (fix the Rust). The G2/G3 skip lists are the only judgment calls and
are fully justified by the Rust type system.
