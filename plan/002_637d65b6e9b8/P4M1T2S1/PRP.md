# PRP — P4.M1.T2.S1: Pin qmk_notifier crate to v0.3.0 tag in Cargo.toml

## Goal

**Feature Goal**: Repoint the `qmk_notifier` git dependency in `Cargo.toml` from
the `v0.2.1` tag to the `v0.3.0` tag so the crate exposes the typed-command
transport API (`CommandResponse`, `RunCommand::{QueryInfo,QueryCallback,SetOs,
ApplyHostContext}`, `HostOs`) that `src/core/notifier.rs` already consumes — and
restore a **green build** (the tree currently does not compile).

**Deliverable**: A 1-line dependency-pin edit in `Cargo.toml` + a refreshed
`Cargo.lock` (via `cargo update -p qmk_notifier`) + an updated Cargo.toml
comment (Mode A). No source-code changes are expected.

**Success Definition**:
- `cargo build` compiles with zero errors (it currently fails with 2×
  `E0412 cannot find type CommandResponse`).
- `cargo test --bin qmkonnect -- --test-threads=1` passes (AGENTS.md mandates
  single-threaded — shared global debouncer `STATE`).
- `Cargo.toml` pins `tag = "v0.3.0"` and the comment states the v0.3.0 bump
  reason (typed-command transport API).
- `Cargo.lock` entry for `qmk_notifier` shows `version = "0.3.0"` sourced from
  `...?tag=v0.3.0`.

## Why

- **Unblocks the build.** P4.M1.T1.S1 (commit `ced887a`) added
  `Notifier::send_command` / `QmkNotifier::send_command`, which reference
  `qmk_notifier::CommandResponse` and the typed `RunCommand` variants — types
  that exist only in v0.3.0. The Cargo pin was left at v0.2.1, so **the tree is
  currently un-buildable** until this task completes.
- **Dependency for downstream.** PRD §8(4)/(5) (host-context send) and the whole
  P4.M2 handshake + P4.M3 send-logic ride on `send_command`, which cannot compile
  without this pin bump. The output ("Updated Cargo.toml pinning v0.3.0") is the
  stated input to P4.M1.T1.S1 consumption and all downstream P4 tasks.
- **Reproducible CI/release.** Tagged-release pinning (vs. branch) keeps builds
  reproducible — preserve that convention (see h2.14 Repository Layout note).

## What

User-visible behavior is unchanged (this is a build/dependency change, no runtime
behavior delta). Technically:

1. `Cargo.toml` dependency line: `tag = "v0.2.1"` → `tag = "v0.3.0"`.
2. `Cargo.lock` `qmk_notifier` entry: version `0.2.1` → `0.3.0`, source
   `?tag=v0.3.0`.
3. Cargo.toml comment (Mode A) notes the bump reason.
4. No `.rs` file is modified (validated — see Context).

## ⚠️ Critical Prerequisite — the v0.3.0 git tag is missing

Research (`git ls-remote --tags https://github.com/dabstractor/qmk_notifier`)
shows the remote has **only** `v0.1.0`, `v0.2.0`, `v0.2.1`. Plan item
**P1.M1.T4.S1** ("tag v0.3.0") is marked Complete, but the tag was never pushed.
The crate's default branch **is** at `version = "0.3.0"` with the full API the
consumer needs (verified by an isolated compile proof — see research notes
"Key finding 5"). Pinning `tag = "v0.3.0"` will therefore fail unless the tag is
created first.

**Step 0 (do this FIRST):**
```bash
git ls-remote --tags https://github.com/dabstractor/qmk_notifier 'refs/tags/v0.3.0'
```
- **Non-empty output** → the tag exists; proceed to Implementation Tasks (Path A,
  the happy path) and just change the Cargo tag.
- **Empty output** → the tag is missing. Pick a resolution:

### Resolution Path A — honor the contract (cut the tag, then pin by tag) — PREFERRED
If you have push rights to `dabstractor/qmk_notifier` (this is a three-repo
project; see PRD h2.80), cut the tag from the default branch HEAD (which is at
Cargo.toml `version = "0.3.0"`):
```bash
cd <qmk_notifier checkout>          # the crate repo, NOT qmkonnect
git fetch origin && git checkout a606f645e4dbca79ab33adc18e2159bd5277123d
git tag -a v0.3.0 -m "v0.3.0: typed-command transport (CommandResponse, RunCommand variants, HostOs)"
git push origin v0.3.0
```
Then proceed to the Implementation Tasks below (edit Cargo.toml `tag = "v0.3.0"`).
This is the path that matches the task contract ("INPUT: Crate tag v0.3.0 from
P1.M1.T4.S1") and keeps the reproducible-tag convention.

### Resolution Path B — interim rev pin (unblock this repo immediately)
If you cannot push the tag, pin by the verified commit SHA so the build is green
**and reproducible** until the tag is cut. Replace the Cargo.toml `tag = "v0.2.1"`
key with `rev`:
```toml
qmk_notifier = { package = "qmk_notifier", git = "https://github.com/dabstractor/qmk_notifier", rev = "a606f645e4dbca79ab33adc18e2159bd5277123d" }
```
This commit is the default-branch HEAD at `version = "0.3.0"` and is the exact
revision validated by the API-compile proof. **Document in the comment that this
is an interim rev-pin pending the v0.3.0 tag**, and that it should be switched
back to `tag = "v0.3.0"` once Path A is done. (A rev pin is fully reproducible,
unlike a branch pin — do NOT use `branch =`.)

> **Path B is the fallback.** Prefer Path A so the lockfile records
> `?tag=v0.3.0` (the success criterion). If you take Path B, flag it in the task
> handoff so P1.M1.T4.S1's tag-cut can be reconciled.

## Anti-Patterns to Avoid
- ❌ Don't refactor `notify()` to "handle" the new `CommandResponse` — the `Ok(_)`
  arm already discards it and compiles. Editing it is out of scope and risks
  breaking the legacy string path.
- ❌ Don't switch to `branch = "main"`/`"master"` to "make it build" — that is
  non-reproducible and breaks the release convention. Use tag (Path A) or rev (Path B).
- ❌ Don't run tests multi-threaded — global debouncer `STATE` is shared;
  `--test-threads=1` is required (AGENTS.md).
- ❌ Don't edit `src/core/notifier.rs`, `Cargo.lock` by hand, or any other `.rs`
  file. Let `cargo update -p qmk_notifier` rewrite the lockfile.
- ❌ Don't declare success if the v0.3.0 tag was missing and you silently pinned
  `master` — document the choice (Path A vs B) in the task handoff.
