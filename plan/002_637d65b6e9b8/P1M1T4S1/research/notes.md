## 2. Release convention (proven by v0.2.1 — the model to copy)

The crate's most recent release (v0.2.1) establishes the EXACT convention:

1. **Dedicated bump commit.** The tag points at commit `32986053` whose subject is
   exactly `bump version to 0.2.1` — a standalone commit that changes ONLY the
   version. T4.S1 mirrors this: `bump version to 0.3.0`.
2. **ANNOTATED tag, not lightweight.** `git cat-file -t v0.2.1` ⇒ `tag` (annotated).
   Message: `Release v0.2.1 — device handle caching`. So:
   `git tag -a v0.3.0 -m "Release v0.3.0 — typed-command transport"`.
3. **Tag body = the release notes.** v0.2.1's body is a one-line summary. For v0.3.0
   (a feature release + breaking API change) the body should enumerate the new
   typed-command surface — this IS the Mode A "release notes" (see §5).
4. **No CHANGELOG.md / RELEASE_NOTES.md exists** in the crate. The annotated tag
   message is the crate's release-notes vehicle. Creating a CHANGELOG.md is an
   OPTIONAL Mode A enhancement (Keep a Changelog format); not required by the
   contract ("Update crate CHANGELOG or release notes **if they exist**" — none do).

## 5. What v0.3.0 actually contains (the release-notes content)

From PRD §7 + completed P1.M1.T1–T3 subtasks. The annotated tag body should summarize:

- **BREAKING:** `run()` returns `Result<CommandResponse, QmkError>` (was
  `Result<(), QmkError>`). For a 0.x crate a breaking change bumps the minor
  (0.2.x → 0.3.0) — exactly this release.
- **New:** `HostOs` enum (`Unsure`/`Linux`/`Windows`/`Macos`/`Ios`, mirrors firmware
  `os_variant_t`).
- **New:** `RunCommand` typed variants — `QueryInfo` (0x01), `QueryCallback(u8)`
  (0x02), `SetOs(HostOs)` (0x03), `ApplyHostContext{ layer, callbacks, clear_board }`
  (0x05); `SendMessage(String)` and `ListDevices` retained (legacy).
- **New:** `CommandResponse` enum — `Legacy{matched}`, `Info{proto_ver,
  feature_flags, callback_count, board_rules_present}`, `CallbackName{index, name}`,
  `Ack{ok}`, `Timeout`.
- **Wire:** typed commands build `[0xF0, cmd, args…]` and reuse the SAME ETX-framed
  multi-report chunking as strings (so APPLY_HOST_CONTEXT may span reports).
- **Response parse:** one 32-byte IN report read; `response[0]==0x51` ⇒ typed (decode
  by cmd-echo); `∈ {0,1}` ⇒ Legacy; no reply ⇒ Timeout.
- **Unchanged:** device cache + retry logic, send path, ListDevices enumeration.
- **Scope:** transport-only — the matcher still lives in qmkonnect (this crate does no
  matching). Firmware typed-command handlers land in P1.M2 (not this release).

8. **Push** — `git push origin main` then `git push origin v0.3.0`.

## 9. Risks / gotchas

- **Unpushed tag = failed release.** The downstream pin (P4.M1.T2.S1) resolves over
  HTTPS to origin; a local-only tag breaks it. The push step is mandatory, not
  optional. Gate: `git ls-remote --tags origin v0.3.0` non-empty.
- **Cargo.lock drift.** `cargo build` after the bump must change ONLY the version
  line. If the diff shows dependency version changes, something else moved — STOP and
  investigate (don't bundle unrelated dependency bumps into a release commit).
- **Tagging the wrong commit.** The tag must point at the bump commit (HEAD after
  step 6), not at a pre-bump commit. Run `git rev-parse HEAD` then
  `git rev-parse v0.3.0^{}` to confirm they match.
- **Lightweight vs annotated.** v0.1.0/v0.2.0 were lightweight; v0.2.1 was annotated.
  Copy v0.2.1 (annotated) — it's the most recent and carries the release notes. Do
  NOT regress to a lightweight tag.
- **README conflict.** Do not edit README.md (T3.S2 owns it). If the bump commit
  accidentally stages README.md, unstage it.
- **`cargo-release` is NOT configured** (no `release.toml`). The release is manual,
  by design — do not introduce cargo-release for this tag.
